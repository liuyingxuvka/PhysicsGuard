## Why

PhysicsGuard can validate many physical models, datasets, signals, and project records, but its current hierarchy and ledgers do not yet form one provider-neutral, compositional model that can explain what the target contains, how child outputs feed parent inputs, which source/test/evidence realizes each element, or what a change affects. Its own FlowGuard adoption also does not yet provide one qualified whole-repository software-DNA root from which every behavior, file, public entry point, test, intent, resource, and release surface can be traced. This change turns the existing native model into a living physical-model blueprint while leaving generic software-blueprint ownership to FlowGuard and making the separate PhysicsGuard self-DNA closure explicit.

## What Changes

- Add one native hierarchical PhysicsGuard blueprint with stable element identity, one root, parent/child ownership, typed input/output/state/effect ports, and explicit aggregation of child outputs into parent inputs.
- Add an authoritative external inventory for target modules, equations, variables, files, datasets, tests, evidence, and provider-owned artifacts; omitted or unsupported items remain typed gaps.
- Separate two explicit understanding targets. `declared_consistency` is the lightweight path that checks the supplied model and references without claiming object completeness. `object_dna` additionally requires a native-adapter-discovered source census, one terminal source-to-model mapping for every observed source member, and current native case/result alignment. A lightweight pass MUST NOT be described as object-DNA readiness.
- Bind every qualified blueprint element to its native model semantics and to exact implementation/workflow, test, dataset, evidence, and target references with current fingerprints.
- Add affected-only impact analysis and reverse trace from a model output or project claim to the underlying physical elements, inputs, equations, files, tests, and evidence.
- Add a provider-neutral interchange and CLI surface for YAML/JSON/native adapters; the directory containing the canonical blueprint is its single artifact root for forward-relative local paths, and Python source is one possible target material rather than the model boundary.
- Require every behavior-bearing physical element and per-module semantic record to expose one exact transition-and-oracle contract: `Input + PreState -> Output + PostState + Effect`, together with preconditions, protected failures, termination, and a source-independent oracle. A field list, source signature, or prose summary cannot substitute for that contract.
- Add deterministic in-memory and directory-native projections for hierarchy,
  interface, state-transition, affected-impact, and reverse-trace slices. The
  blueprint directory, model files, tests, bindings, and evidence remain the
  object DNA; projections preserve every omitted-artifact gap and never create
  a second DNA authority or a generated target.
- Require release qualification against at least one real non-self target whose subject, target material, engineering meaning, tests/observations, and ownership exist independently of PhysicsGuard's own source, prompts, checker, or qualification fixtures. A repository-authored demonstration remains useful regression evidence but cannot alone license the real-target capability claim.
- Add a later-bound FlowGuard projection that consumes the qualified PhysicsGuard blueprint without duplicating FlowGuard's generic blueprint, inventory, or affected-reader implementation.
- Define one separate FlowGuard-owned software-DNA root for the whole PhysicsGuard repository, with child behavior models, exact `Input × State -> Set(Output × State)` contracts, whole-repository disposition/ownership, code-test-intent-resource-topology bindings, deterministic affected/reverse indexes across Python and non-Python surfaces, and the seven stable provider-neutral depth layers: evidence qualification, implementation inventory, traceability, independent semantics, model-code-test binding, resource-oracle binding, and static blueprint readiness.
- Treat the repository-native FlowGuard definition, model hierarchy, code/test/resource bindings, affected/reverse indexes, and current evidence references as PhysicsGuard's sole software DNA. Expose one read-only in-place `self-dna check` projection, including a compact form that preserves the first gap, and do not add a standalone export, materialization, reconstruction exercise, release asset, cache authority, or second DNA head.
- Make object-DNA admission depend on one provider-neutral native-observation contract. Preserve FMI as one strict adapter profile and add one bounded structured-object profile so non-FMI software, experiments, documents, models, or workflows can supply the same independently replayed source-census/case/result boundary without an FMI special case in the reviewer.
- Replace the current grouped navigation module/equation ledger directly with one current per-module semantic ledger. Resolve all members of the frozen 152-member public registry baseline without grandfathering the existing 39 modeled members: independently review 37 mechanically draftable members, apply domain judgment to 75 members, and retain `DummyResidualModule` in this patch as `supporting_framework_behavior` with `physical_claim_licensed=false` and an independent software-behavior/test semantic record.
- Update all ten PhysicsGuard skill routes and prompt bundles so light use loads only the relevant summary or affected slice while deep claims require the native blueprint receipt.
- Remove or reject silent fallback, compatibility readers, duplicate authority, incomplete denominator, self-fingerprinted export, proof-free architecture reduction, and summary-only evidence paths exposed by the new blueprint.

## Capabilities

### New Capabilities

- `physics-domain-blueprint`: Native hierarchical physical-system, experiment, testbench, or workflow blueprint with typed ports, identities, inventories, bindings, and qualification.
- `physics-blueprint-impact-trace`: Affected-only impact traversal and reverse trace across native physical elements, artifacts, tests, datasets, evidence, and parent/child interfaces.
- `physics-blueprint-interchange`: Target-neutral serialization, CLI operations, adapter contract, and later-bound FlowGuard projection boundary.

### Modified Capabilities

- `physics-model-deepening`: Deepening must preserve parent/child refinement, compositional interfaces, independent target inventory, first unresolved gap, and the deepest currently licensed layer.
- `simulation-validation-depth`: Broad validation must bind each governed model element to exact native simulations, scenarios, files, datasets, observations, and tests rather than aggregate counts.
- `physicsguard-skill-suite-runtime-authority`: Each maintained skill route must publish and consume its exact native blueprint slice, retain one direct authority, and keep light/deep loading bounded.
- `physicsguard-narrow-skill-entry-loading`: Blueprint check, impact, and trace references are loaded only for the selected route and affected model slice.

## Impact

FMI is the first concrete source-census adapter, not a language, runtime, or vendor boundary. Other software, experiment, testbench, paper-supporting model, and workflow adapters can emit the same provider-neutral census and native-result contract.

This affects the PhysicsGuard schema, hierarchy, direct-current per-module semantic ledger, CLI, loaders, model/test/evidence registries, validation-depth checks, ten maintained skill prompts and contracts, focused and integration tests, FlowGuard adoption/model sources after the external FlowGuard upgrade stabilizes, the installed skill projection, and the patch release boundary. Existing native solvers and domain checks remain the semantic owners; the blueprint composes their current results instead of replacing them with a second evaluator. Ordinary changes use the exact affected closure; whole-DNA static review is reserved for bootstrap/backfill, an explicit whole-boundary request, architecture-reduction closure, or a frozen release gate. Static blueprint readiness does not by itself establish current test execution, installation, Git commit, tag, or GitHub release readiness; those remain separate executable or lifecycle claims. The native software-DNA files are reviewed where they live and are never exported as another canonical product.
