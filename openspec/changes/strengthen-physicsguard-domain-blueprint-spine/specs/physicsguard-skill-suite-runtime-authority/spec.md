## ADDED Requirements

### Requirement: Every maintained route binds its native blueprint slice
Each of the ten maintained PhysicsGuard skill routes SHALL declare which physical-blueprint element, relation, inventory, binding, layer, or affected-slice identities it produces, consumes, or leaves not applicable. A route supporting a deep, broad, closure, reuse, prediction, or candidate-model claim MUST consume a current target-native blueprint receipt for its exact scope. SkillGuard SHALL supervise identities and evidence but MUST NOT decide physical semantics or create a second blueprint authority.

#### Scenario: Deep skill claim omits blueprint receipt
- **WHEN** a maintained route claims deep understanding, broad validation, closure, reuse, prediction, or candidate readiness without its exact current blueprint receipt
- **THEN** the target-native result and SkillGuard closure remain non-pass

#### Scenario: Route has no applicable blueprint mutation
- **WHEN** a bounded route only reads an affected current slice and changes no blueprint-owned element or binding
- **THEN** it records that consumption without fabricating a new blueprint revision

#### Scenario: SkillGuard supplies physical meaning
- **WHEN** a generic author field or supervisor result attempts to define an equation, physical interface, refinement, validity boundary, or blueprint layer status
- **THEN** the contract is rejected because PhysicsGuard retains the physical-domain owner

### Requirement: Candidate blueprint route owns native blueprint review
`physicsguard-candidate-model-blueprint` SHALL be the single direct skill owner for authoring or reviewing the canonical physical-domain blueprint. Its author contract SHALL name the exact PhysicsGuard schema/core/CLI known-good and known-bad checks that prove target identity, inventory, compositional interfaces, semantics, native bindings, currentness, derived layer status, and safe claim behavior. No other route SHALL duplicate its qualification predicate.

#### Scenario: Prompt-only candidate proof is supplied
- **WHEN** the candidate route provides a structurally plausible prompt or guard-model fixture but does not execute the native blueprint reviewer
- **THEN** candidate capability and author closure remain non-pass

#### Scenario: Candidate prompt omits target inventory authority
- **WHEN** the candidate route instructs `blueprint review` without the required `--target-authority AUTHORITY` input
- **THEN** prompt validation blocks the route because that command cannot execute the single current reviewer contract

#### Scenario: Another skill reimplements blueprint readiness
- **WHEN** another maintained route derives its own blueprint-ready status instead of consuming the candidate route's current native result
- **THEN** suite validation blocks the duplicate authority

### Requirement: Skill results preserve affected and whole-scope distinctions
Every blueprint-aware skill result SHALL bind either an exact affected-slice fingerprint or an explicit whole-boundary fingerprint, preserve omitted members as outside scope rather than passed, and expose stale, blocked, unsupported, unresolved, and not-applicable outcomes distinctly. A route MUST NOT broaden automatically to all skills, all blueprint members, or all native checks.

#### Scenario: Local signal review consumes an affected slice
- **WHEN** signal mapping affects one interface path
- **THEN** the signal route consumes that affected slice and its required ancestors and evidence without loading or validating unrelated physical branches

#### Scenario: Whole-model closure is requested
- **WHEN** the requested claim covers the complete declared target boundary
- **THEN** the closure route requires whole-inventory blueprint qualification and current child results for every required route

### Requirement: Author and consumer projections preserve blueprint currentness
The author source, generated prompt references, installed consumer skills, native runtime requirement, and blueprint-aware contract projections SHALL bind the exact released PhysicsGuard version and current route-owned blueprint semantics. A change to a blueprint-aware prompt, capsule, native protocol, guard model, execution-depth policy, runtime check, or package version SHALL invalidate only its exact consumers and the required parent reattachment.

#### Scenario: Installed skill has an older blueprint protocol
- **WHEN** the source skill requires the current physical blueprint receipt but the installed projection still contains an older protocol or runtime version
- **THEN** installation-currentness and any dependent production claim are stale

#### Scenario: One route protocol changes
- **WHEN** one route's blueprint input or output contract changes
- **THEN** that route's exact checks and parent projection are revalidated while unrelated route receipts remain reusable when their declared inputs are unchanged

### Requirement: Consumer installation has one current SkillGuard authority
PhysicsGuard SHALL freeze only the exact ten-member suite identity and the
prepare, verify, activate, and rollback ordering. Source consumer plans,
consumer-file selection, manifest and release identity, author-control
exclusion, path and symlink safety, stage construction, activation locks,
journals, receipts, recovery, and rollback SHALL be owned by the explicitly
selected current installed SkillGuard public API. The read-only readiness audit
SHALL consume the same installed-suite checker result and MUST NOT implement a
second consumer comparison algorithm. Missing, foreign, or incomplete
SkillGuard authority SHALL block visibly with no local fallback.

#### Scenario: A new source file is absent from the installed projection
- **WHEN** any maintained skill gains a consumer-eligible source file after its installed release was built
- **THEN** the current SkillGuard source plan derives a different full file list and release id and the installed-suite audit blocks that member as stale

#### Scenario: Installed identity or filesystem content is unsafe
- **WHEN** an installed member has a missing or rehashed-but-wrong release id, invalid or missing manifest, `.skillguard` author path, symbolic-link root, missing declared file, or unexpected file
- **THEN** the path preflight or current SkillGuard audit blocks the member and readiness cannot pass

#### Scenario: Read-only currentness is requested
- **WHEN** the installed-suite checker or readiness audit compares source and installed projections
- **THEN** it creates no stage, receipt, lock, journal, install, rollback, source update, or installed-file update

#### Scenario: Exact-ten activation begins
- **WHEN** all ten source plans are current and suite installation is requested
- **THEN** all ten stages are prepared and all ten are verified through SkillGuard before the first activation

#### Scenario: A later activation fails
- **WHEN** one member activation blocks after earlier members were activated successfully
- **THEN** the coordinator invokes SkillGuard rollback for every earlier successful activation in reverse order and reports any rollback failure without hiding the original activation block

#### Scenario: Current installation API is unavailable
- **WHEN** the selected installed SkillGuard root or any required public installation callable is missing, unsafe, or owned by another path
- **THEN** planning or installation remains visibly blocked and PhysicsGuard does not run a copied installer or consumer validator

### Requirement: Family process evidence has one non-domain owner
The ten maintained members SHALL retain their exact physical-domain and model
owners. Generator currentness, the root TestMesh definition, exact-ten
distribution and installation ordering, installed currentness, and readiness
projection SHALL be covered by exactly one family-level process owner. That
owner MAY be declared in one registered member as a schema placement detail,
but its identity, evidence domain, inputs, and claim boundary SHALL remain
family-level and SHALL NOT license that member's physical-domain result.

#### Scenario: A maintenance file changes
- **WHEN** the generator, root TestMesh checker, suite installer, installed-currentness checker, or readiness projection changes
- **THEN** the one family process owner becomes affected and the ten physical-domain owners do not become affected unless one of their own declared inputs also changed

#### Scenario: Family process evidence is used as a physical claim
- **WHEN** a family generation, installation, currentness, or readiness receipt is presented as evidence that a physical model, dataset, mapping, or audit closure is correct
- **THEN** the claim is rejected because process evidence owns no physical-domain predicate

### Requirement: Root topology audit executes once
The single root TestMesh static audit SHALL verify the exact ten-member,
84-domain-owner, one-family-process-owner topology, component mappings,
source-only author controls, and blocked unknown mapping without executing any
owner. A member-local route check SHALL NOT repeat the complete root audit and
SHALL bind only its own prompt, guard model, route contract, and exact native
implementation/test inputs.

#### Scenario: One member route changes
- **WHEN** one route-specific physical blueprint implementation or test changes
- **THEN** its already existing direct member owner is selected and the family root audit remains one static topology check rather than ten repeated full audits

### Requirement: A representative external physical target qualifies the domain capability
Before release closure for this change, PhysicsGuard SHALL use the public physical-domain blueprint workflow on an independently inventoried representative external physical system, experiment/testbench, simulation model, or mixed physical workflow. The target SHALL exercise a non-trivial parent/child physical hierarchy, typed interfaces, state/effects, physical semantics, refinement, native bindings, validation evidence, and resource/oracle bindings. PhysicsGuard software modules, prompts, and skills MUST NOT be reclassified as physical target elements for this qualification. At least one release-qualifying target SHALL be real and non-self: its target identity, raw material, engineering semantics, observations/tests, and evidence ownership SHALL exist independently of PhysicsGuard source, prompts, schema examples, checker implementation, and qualification fixtures. A PhysicsGuard-authored example MAY prove regression mechanics but SHALL NOT alone license real-target qualification.

#### Scenario: External target inventory exposes an omitted element
- **WHEN** the independent target inventory contains a physical element, interface, semantic obligation, native binding, test, dataset, evidence item, oracle, or resource that is absent or undispositioned in the blueprint
- **THEN** target qualification remains incomplete and the result identifies the exact missing member and first unsupported depth

#### Scenario: External target passes its declared boundary
- **WHEN** the exact declared target boundary, inventory, hierarchy, physical semantics, bindings, tests, resources, and evidence pass the canonical current reviewer
- **THEN** the result may support capability qualification only for that external target and achieved depth and does not prove universal target coverage

#### Scenario: Only a self-authored qualification fixture is available
- **WHEN** the only passing target, expected answers, target material, and evidence were authored as part of PhysicsGuard's own qualification tests
- **THEN** regression capability may pass but real non-self target qualification remains blocked on independent target ownership and evidence

#### Scenario: Real target access is bounded
- **WHEN** a real independently owned target exposes only a subset of its artifacts or engineering evidence
- **THEN** PhysicsGuard preserves the exact inaccessible members and achieved depth as gaps rather than replacing them with fixture data or a universal capability claim

### Requirement: PhysicsGuard software DNA remains a FlowGuard-owned artifact
PhysicsGuard's own software structure SHALL be modeled and reviewed through exactly one FlowGuard-owned whole-repository software-DNA root with recursively compositional child behavior models. The independently frozen denominator SHALL cover every release-governed behavior, tracked file, public import, command/subcommand, script entry point, package/build input, ten-skill prompt and route surface, OpenSpec intent, documentation/example/template, test/fixture, configuration, model source, resource, installation surface, and release surface. Python and non-Python members SHALL be accounted identically. Every denominator member SHALL have exactly one terminal disposition and one primary owner; missing, duplicate, or unresolved disposition or ownership SHALL block whole-DNA qualification.

The software behavior that authors, reviews, impacts, traces, or validates a `PhysicalModelBlueprint` SHALL be one product-function subtree under the FlowGuard software-DNA root. A `PhysicalModelBlueprint` instance SHALL remain an external physical-target artifact, SHALL NOT be the software-DNA root, SHALL NOT replace the whole-repository denominator, SHALL NOT count as representative external-target qualification for the software itself, and SHALL NOT license any physical-domain claim about PhysicsGuard's implementation.

#### Scenario: Final software-structure audit is requested
- **WHEN** the release workflow audits PhysicsGuard's own modules, CLI paths, skill prompts, tests, resources, duplicate owners, or architecture-reduction candidates
- **THEN** it consumes the current FlowGuard software blueprint and its code/test/resource bindings separately from the external physical-target blueprint review

#### Scenario: Physical blueprint is proposed as the self-DNA root
- **WHEN** a `PhysicalModelBlueprint`, representative physical target, or external-target review is proposed as the root or denominator of PhysicsGuard's software self-model
- **THEN** software-DNA qualification blocks and requires the single whole-repository FlowGuard root

#### Scenario: A non-Python surface is omitted
- **WHEN** a YAML or JSON contract, OpenSpec requirement, prompt/reference file, template, example, documentation promise, shell entry point, installation record, or release surface is inside the release-governed repository boundary but has no terminal disposition and primary owner
- **THEN** whole-DNA inventory closure is non-pass even when every Python module is mapped

#### Scenario: A repository member has two owners
- **WHEN** two child models claim primary ownership of the same behavior, file, or public entry point
- **THEN** neither owner is selected by ordering and whole-DNA qualification blocks on that exact duplicate

### Requirement: Software DNA uses the seven stable provider-neutral depth layers
Every behavior-bearing software-DNA node SHALL express `Input × State -> Set(Output × State)` with explicit failures, effects, preconditions, postconditions, and termination where applicable. Parent and child models SHALL account for every required input, state source, output consumer, next-state transition, and effect boundary. Each node SHALL bind bidirectionally to its governing intent, Python or non-Python implementation, public entry point, tests and counterexamples, oracles and current evidence, resources and provider-owned dependencies, and parent/child, sibling, call, data, state, installation, and release topology.

FlowGuard SHALL derive these seven ordered software-DNA layers and no project-specific replacement order: evidence qualification; implementation inventory; traceability; independent semantics; model-code-test binding; resource-oracle binding; and static blueprint readiness. The deepest licensed layer SHALL be the last contiguous passing layer. A later passing fragment, caller declaration, cached summary, or physical-blueprint result MUST NOT skip an earlier gap.

The whole-repository denominator and its dispositions are implementation-inventory obligations. The one-root child hierarchy, intent links, parent/child and sibling topology, and deterministic affected/reverse relations are traceability obligations. FunctionBlock behavior independent of source location is an independent-semantics obligation. Exact implementation and test owners belong to model-code-test binding, while prompts, schemas, configuration, datasets, provider resources, counterexamples, and oracles belong to resource-oracle binding. Root structure, topology, affected/reverse indexes, external materialization, or release publication MUST NOT be introduced as substitute depth layers.

#### Scenario: Child output has no software consumer
- **WHEN** a child FunctionBlock output, state transition, or effect is neither consumed by a sibling or parent nor exported or terminally dispositioned
- **THEN** traceability or independent-semantics closure fails at the exact child relation and later software-DNA layers remain unlicensed

#### Scenario: Intent is not bound
- **WHEN** code and tests are mapped but an externally visible behavior has no governing OpenSpec requirement, project rule, or public promise binding
- **THEN** implementation inventory may remain visible while traceability and later layers are non-pass

#### Scenario: A later layer is green after an earlier gap
- **WHEN** a resource-oracle binding is current but one repository file has no primary owner or one FunctionBlock has an open traceability edge
- **THEN** the deepest licensed static layer stops before that earlier gap and static blueprint readiness remains non-pass

#### Scenario: Static blueprint readiness passes without current execution or release evidence
- **WHEN** all seven static layers pass but current test execution, package build, installation, Git commit, tag, GitHub release, or release-asset evidence is absent
- **THEN** PhysicsGuard may report bounded static blueprint readiness only and every unexecuted or unpublished lifecycle claim remains not run or unverified

### Requirement: Software DNA affected and reverse indexes separate ordinary work from whole-boundary gates
The qualified software-DNA graph SHALL produce one deterministic affected index and reverse index across behaviors, files, entry points, intents, tests, evidence, resources, child models, and release surfaces. Ordinary maintenance SHALL consume the smallest exact affected closure plus required ancestors, connected siblings, and shared consumers. Whole-DNA review SHALL be selected only for initial backfill, an explicit whole-boundary request, an ambiguity that prevents bounded scope, final architecture-reduction closure, or a frozen release gate. Unknown or ambiguous relations SHALL block the bounded result; FlowGuard and PhysicsGuard MUST NOT silently select an owner, reuse a stale slice, fall back to repository scanning, or automatically run all work.

#### Scenario: One bounded skill prompt changes
- **WHEN** one skill prompt and its exact route, intent, tests, shared references, and parent projection form a closed affected slice
- **THEN** ordinary validation selects that slice and leaves unrelated product and release branches outside scope rather than passed

#### Scenario: A reverse trace reaches an ambiguous owner
- **WHEN** a public command or release claim traces to two possible implementation or test owners without a current typed relation
- **THEN** reverse trace stops at the ambiguity and cannot license code change, reduction, or release

#### Scenario: Frozen release is evaluated
- **WHEN** source, toolchain, model, test, install, and version identities are frozen for release
- **THEN** the workflow explicitly runs whole-DNA static qualification as one release input rather than treating prior affected-only results as whole-repository or release evidence

### Requirement: Canonical software DNA materialization and release publication are separate gates
The canonical transferable software-DNA bundle SHALL materialize one exact static result from a frozen repository snapshot into an explicitly selected artifact root outside the repository. The bundle SHALL contain or bind the root, child models, denominator, typed relations, affected/reverse indexes, seven layer results, fingerprints, first gap, deepest licensed layer, and bounded claim without upgrading a non-pass result. Repository-local model sources and generators SHALL remain governed inventory members, but the canonical output SHALL NOT be written inside the repository or used as an input to its own fingerprint. No in-repository canonical copy, cache authority, compatibility export, legacy reader, alias, fallback, or second current head SHALL exist. Materialization is an identity-preservation gate outside the seven static layers.

For a release that claims current software DNA, current test execution, package build, installation, installed-skill projection, Git commit, tag, and GitHub release evidence SHALL be established separately before the canonical bundle and its manifest can support release-asset closure. The manifest SHALL bind bundle fingerprint, denominator fingerprint, source commit, package version, and claim boundary, and the published assets SHALL be independently downloaded and verified. The bundle SHALL remain outside the package wheel, source distribution, installed package, and installed consumer skills. Source commit, package, installation, skill projection, Git tag, GitHub release, and software-DNA asset SHALL remain separate identities and claim boundaries. Release publication is a lifecycle gate and contributes no static depth.

#### Scenario: Export path is inside the repository
- **WHEN** the selected canonical bundle path is under the repository boundary
- **THEN** export blocks before writing because the bundle would enter the denominator it fingerprints

#### Scenario: Bundle is embedded in the package
- **WHEN** the canonical software-DNA bundle appears in a wheel, source distribution, installed package, or installed consumer skill
- **THEN** packaging and installation closure fail because the release asset boundary has been crossed

#### Scenario: Release asset does not match the frozen source
- **WHEN** a published or downloaded bundle names another source commit, version, denominator, or bundle fingerprint
- **THEN** the software-DNA release claim fails without promoting another local copy or cached export

#### Scenario: Static bundle is current but release evidence is missing
- **WHEN** the external bundle exactly materializes a static-ready blueprint but package, installation, Git/tag, GitHub release, or downloaded-asset evidence is missing
- **THEN** the static and materialization identities remain reportable while release-asset closure remains non-pass

### Requirement: Architecture reduction accepts only proof-ready candidates
Architecture reduction SHALL consume the current whole-repository software DNA and SHALL change only candidates whose observable contract, single primary owner, consumers, affected and reverse closure, code/test/intent/resource bindings, parity oracle, target action, migration impact, and rollback boundary are current and unambiguous. Public command, facade, package, or large-module changes SHALL use the owning structure route, and field or schema removal SHALL use lifecycle evidence. Accepted replacement SHALL remove the old path directly; no compatibility shim, alias, fallback handler, legacy reader, alternate command, or duplicate success route SHALL remain.

#### Scenario: Two handlers look duplicated but proof is incomplete
- **WHEN** handlers have similar names or code but their public contracts, consumers, affected tests, or state/effect behavior are not proven equivalent
- **THEN** the candidate is retained or deferred and no architecture edit is licensed

#### Scenario: A merge is proof-ready
- **WHEN** one candidate has exact contract parity, a sole surviving owner, complete affected and reverse closure, current parity evidence, and a bounded rollback plan
- **THEN** direct-current reduction may merge or delete the replaced path and must rerun the affected software-DNA and parity checks
